# 通知

`.env` に Webhook URL を設定すると、インシデントの変化を Discord / Slack へ通知します。
どちらも Incoming Webhook を使うため、追加のパッケージやトークンは不要です。

通知するのは、前回の通知内容から変化したものだけです。

| 種類 | 通知するタイミング | 見出し |
| --- | --- | --- |
| 新規 | 前回の記録に無いインシデントを検出したとき | 🚨 新しいインシデント: インシデント名 |
| 更新 | 記録時から `updated_at` が変化したとき | 🔄 状況が更新されました: インシデント名 |
| 復旧 | インシデントが解決済みになったとき | ✅ 復旧しました: インシデント名 |

Discord へは Unicode の絵文字をそのまま送り、Slack へはショートコード
（`:rotating_light:` / `:arrows_counterclockwise:` / `:white_check_mark:`）で送ります。
表示される絵文字はどちらも同じです。

- 新規・更新は `impact` に応じて色分けします（`critical` = 赤、`major` = 橙、`minor` = 黄）
- 復旧は影響度に関わらず緑で通知します
- インシデント名から `shortlink` へリンクします
- 復旧の通知には、GitHub が投稿した最後のコメント本文を載せます（長い場合は 300 文字で切り詰めます）
- 1 回の通知に含めるのは 10 件までです（Discord の embeds 上限に合わせています）。
  超過分は見出しに「他 N 件」と表示します
- 変化が 1 件も無いときは通知しません
- 片方の送信に失敗しても、もう片方の送信は継続します

### 復旧の検出

復旧の判定は、公式の過去のインシデント一覧（`incidents.json`）が返す `status` を根拠にします。
記録ファイルに前回の状態が残っているかどうかには依存しません。

1. `incidents.json` で `resolved`（または `postmortem`）になっているインシデント
2. 記録にあるのに、`unresolved.json` にも `incidents.json` にも現れなくなったインシデント

1 が主で、2 は補いです。`incidents.json` は直近 50 件しか返さないため、
長く続いた障害は解決するころには一覧から漏れていることがあります。2 はその救済です。

`incidents.json` に未解決のまま残っているうちは、`unresolved.json` から消えていても
復旧としません。2 つのエンドポイントは別々に取得するため反映がずれることがあり、
そこで復旧としてしまうと誤った通知が飛ぶうえ、通知済みとして記録されて
本当に解決したときの通知まで握りつぶしてしまうためです。

未解決の状態を一度も観測できなかったインシデント（実行間隔より短い障害や、
ツールを止めていた間に始まって終わった障害）も 1 で検出できます。
ただし過去のインシデント一覧には数日前の分も含まれるため、そのまま通知すると
毎回同じ内容が飛んでしまいます。そこで `notified_incidents.json` に
「前回どこまで確認したか」（`last_checked_at`）を記録し、
記録に無いインシデントについては、それより後に解決したものだけを通知します。

- 記録にあるインシデントは、いつ解決したかに関わらず通知します
- `last_checked_at` が無いとき（初回実行や記録を消した直後）は、GitHub 側の観測時刻から
  遡って **24 時間以内**に解決したものだけを通知します。過去の障害がまとめて飛ぶのを
  防ぎつつ、目印ができるまでの間に解決した障害を取りこぼさないためです
- 記録する時刻には、実行するマシンの時計のずれに左右されないよう GitHub 側の時刻を使います
- 目印は巻き戻しません。解決済みのインシデントが直近 50 件から外れると
  GitHub 側の時刻が古くなることがあり、通知済みの復旧が再び飛んでしまうためです
- 通知した復旧は `resolved_notified` に残し、次回以降の対象から外します
  （判定に影響しなくなったものは保存時に取り除くため、際限なく増えることはありません）
- 復旧として通知したインシデントが再び未解決として現れた場合は `resolved_notified` から外し、
  次に解決したときにあらためて通知します

発生中かどうかの判断は、未解決一覧（`unresolved.json`）だけを根拠にします。
両方に載っていることを条件にすると、反映の遅れで発生を取りこぼすためです。
ただし記録の持ち越しは過去のインシデント一覧も見ます。未解決一覧から一時的に消えただけの
インシデントを記録から落とすと、次に現れたときに新規として通知してしまうためです。

復旧の通知に載せる影響度・コンポーネント・発生日時・復旧日時・コメント本文は、
未解決一覧ではなく過去のインシデント一覧から取得します。
過去 50 件から漏れて取得できなかった場合だけ、前回通知した時点の記録
（インシデント名・直前のステータス・前回の更新日時）で代替します。
記録にも名称が残っていない場合は、インシデント ID を見出しに表示します。

コンポーネントは、Status API が各インシデントに付けている `components` から取得します。

通知先の設定を確かめたいときは `-test-notify` でサンプルを送れます。
詳しくは [実行方法とテスト](usage.md#テスト通知) を参照してください。

## 重複通知の抑止

定期実行しても同じインシデントを繰り返し通知しないよう、通知済みのインシデントを
`./notified_incidents.json` に記録しています。

```json
{
    "incidents": {
        "cp306tmzcl0y": {
            "name": "Unplanned Database Outage",
            "status": "identified",
            "updated_at": "2014-05-14T14:35:21.711-06:00"
        }
    },
    "last_checked_at": "2026-08-31T13:54:08.001Z",
    "resolved_notified": {
        "kfspvrz14xr0": "2026-08-31T13:54:08.001Z"
    }
}
```

`last_checked_at` は前回どこまで確認したかを表す目印で、復旧の検出に使います。
`resolved_notified` は復旧を通知済みのインシデントで、二重通知を防ぐために残します。

復旧を通知した後は、`incidents` からそのインシデントの記録を削除します。
未解決のものだけを残すため、ファイルが際限なく増えることはありません。
すべて通知し直したい場合は、このファイルを削除してください
（未解決のインシデントが新規として通知されます。すでに解決した障害は通知されません）。

なお、送信に失敗した場合は記録を更新しないため、次回の実行で再送されます。
`-dry-run` のときと Webhook URL が未設定のときも、実際には送信していないため更新しません。
そのままでは `last_checked_at` がいつまでも残らず、復旧の判定が初回実行のままになります。

`-local` で実行したときの記録は、実 API 用とは別の `notified_incidents.local.json` に残します。
サンプルの日付は実 API とかけ離れており、同じファイルに混ぜると次の実 API 実行で
過去のインシデントが一斉に復旧として飛ぶためです。
